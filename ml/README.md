# SaaS voice RAG

Python-сервис правил качества и оценки транскриптов.
## Что реализовано

- Общие и персональные правила администратора хранятся в PostgreSQL. Требования компаний — отдельный набор, который хранится в отдельной таблице pgvector `company_requirements_v1`.
- Отдельная таблица актуальных правил с `id`, `scope`, `administrator_id`, категорией и версией. При обновлении с тем же `id` номер версии увеличивается.
- При оценке общие и персональные правила администратора загружаются из PostgreSQL. Если передан `company_id`, транскрипт ищет похожие требования только этой компании в pgvector; дубликаты объединяются, в промпт передаются лучшие совпадения (по умолчанию до 10).
- JSON-результат с применимостью, статусом, пояснением, цитатами, speaker/timestamp и частично выполненными пунктами.
- Отказ от числовой оценки, пока вызывающая сторона не передаст шкалу.
- API для управления требованиями, семантического поиска и оценки транскрипта.

## Запуск через Docker

1. Скопируйте `.env.example` в `.env` и укажите адрес внешнего OpenAI-совместимого API Qwen в `LLM_BASE_URL` и при необходимости `LLM_API_KEY`.
2. Запустите из директории `ml`:

   ```sh
   docker compose up --build
   ```

3. API будет доступен на `http://localhost:8000`. Документация OpenAPI: `/docs`.

Локальный запуск API вне Docker требует `POSTGRES_HOST=localhost`; в Compose адрес БД автоматически задаётся как `postgres`.

## API

Добавить/обновить правила:

```json
POST /requirements
{
  "items": [
    {"id": "greeting-v1", "scope": "base", "category": "greeting", "title": "Приветствие", "text": "Менеджер должен поздороваться и представиться."},
    {"id": "client-price", "scope": "administrator", "administrator_id": "admin_123", "category": "pricing", "title": "Цена", "text": "Перед ценой менеджер сообщает об актуальной акции."}
  ]
}
```

Общие требования используют `scope: "base"`. Для персонального правила передайте `administrator_id` и `scope: "administrator"`. Если `scope` опущен, сервис определяет его по наличию `administrator_id`. Для обновления передайте тот же `id`, при добавлении нового правила ID можно опустить.

Получить активные общие и персональные для администратора правила: `GET /requirements?administrator_id=admin_123`. Архивировать: `DELETE /requirements/{id}`.

Добавить требования компании в отдельную векторную базу:

```json
POST /company-requirements
{
  "company_id": "company_123",
  "items": [
    {"id": "pricing-policy", "title": "Условия цены", "category": "pricing", "text": "Для этой компании перед озвучиванием цены нужно уточнить комплектацию."}
  ]
}
```

Для обновления правила компании передайте ту же пару `company_id` и `id`. При повторной отправке с той же парой запись обновится.

Оценить транскрипт:

```json
POST /evaluate
{
  "administrator_id": "admin_123",
  "company_id": "company_123",
  "transcript": "00:00 Менеджер: Здравствуйте, меня зовут ...",
  "score_scale": null
}
```

`administrator_id`, `company_id` и `score_scale` можно передавать независимо. `retrieval_k` ограничивает только число найденных требований компании (по умолчанию 10, максимум 50). В `retrieved_requirements` перечислены все правила, переданные модели. У правил компании есть поле `distance` с расстоянием при поиске. Статусы критериев: `fulfilled`, `partially_fulfilled`, `not_fulfilled`, `insufficient_information`, `not_applicable`, `conflict`.

`POST /search` ищет только требования указанной компании в pgvector; нужен `company_id`. `POST /evaluate` всегда добавляет общие и персональные правила администратора из PostgreSQL, а если передан `company_id`, дополнительно ищет подходящие требования этой компании по транскрипту. Требования компании не заменяют и не фильтруют обязательные правила администратора. По умолчанию сервис возвращает ближайшие совпадения даже при слабом сходстве; `retrieval_k` и порог релевантности нужно проверить на размеченных звонках.

## Замена модели

LLM задаётся через `LLM_BASE_URL`, `LLM_API_KEY` и `LLM_MODEL`; требуется OpenAI-совместимый API. Модель эмбеддингов задаётся через `EMBEDDING_MODEL`, устройство — `EMBEDDING_DEVICE`. При замене embedding-модели нужно одновременно пересоздать/мигрировать коллекцию и выставить правильный размер вектора в `config.py`.

## Важные ограничения перед эксплуатацией

- Таблица `rag_requirements` создаётся автоматически. Старые правила с `client_id` сохраняются в базе и исключаются из оценки. Чтобы вернуть их в оценку, заново загрузите нужное правило через `/requirements` с явным `administrator_id` или через `/company-requirements` с явным `company_id`. Для новых запросов передавайте эти поля вместо `client_id`.
- При обновлении правила с `id` хранится только актуальная запись и её номер версии; история текста для аудита пока не ведётся.
- API предназначен для внутреннего вызова доверенным backend. Перед публикацией наружу нужно добавить аутентификацию, tenant authorization, лимиты запросов и ограничение размера транскрипта.
- Поиск требований компании идёт по фрагментам транскрипта, чтобы учитывать начало и конец длинного разговора; найденные правила дедуплицируются перед запросом к LLM.
- Точные цитаты проверяются на наличие в исходном транскрипте; speaker и timestamp сохраняются, если модель их вернула.
- Качество и полнота векторного поиска ещё требуют калибровки на обезличенном массиве звонков вместе с заказчиком; `retrieval_k` увеличивает охват, но также добавляет лишние совпадения и токены.
