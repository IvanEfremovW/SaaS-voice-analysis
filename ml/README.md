# SaaS voice RAG

Python-сервис правил качества и оценки транскриптов.
## Что реализовано

- Хранение правил в PostgreSQL и семантический поиск через pgvector.
- Отдельная таблица актуальных правил с `id`, `scope`, `client_id`, категорией и версией. При обновлении с тем же `id` номер версии увеличивается, прежний embedding заменяется.
- Полная оценка каждого активного базового правила и правил заданного клиента. Оценка берёт полный чек-лист из таблицы требований и не ограничивается top-k поиском.
- JSON-результат с применимостью, статусом, пояснением, цитатами, speaker/timestamp и частично выполненными пунктами.
- Отказ от числовой оценки, пока вызывающая сторона не передаст шкалу.
- API для управления требованиями, семантического поиска и оценки транскрипта.

## Запуск через Docker

1. Скопируйте `.env.example` в `.env` и укажите адрес внешнего OpenAI-совместимого API Qwen в `LLM_BASE_URL` и при необходимости `LLM_API_KEY`.
2. Запустите из директории `ml`:

   ```sh
   docker compose up --build
   ```

3. API будет доступен на `http://localhost:8000`. Документация OpenAPI: `/docs`.

Локальный запуск API вне Docker требует `POSTGRES_HOST=localhost`; в Compose адрес БД автоматически задаётся как `postgres`.

## API

Добавить/обновить правила:

```json
POST /requirements
{
  "items": [
    {"id": "greeting-v1", "scope": "base", "category": "greeting", "title": "Приветствие", "text": "Менеджер должен поздороваться и представиться."},
    {"id": "client-price", "scope": "client", "client_id": "client_abc", "category": "pricing", "title": "Цена", "text": "Перед ценой менеджер сообщает об актуальной акции."}
  ]
}
```

Для обновления требования передайте тот же `id`; новые правила получают ID автоматически. Для клиентского требования обязательны `scope: "client"` и `client_id`. Без `scope` правило с `client_id` считается клиентским, иначе базовым.

Получить активные общие и клиентские правила: `GET /requirements?client_id=client_abc`. Архивировать: `DELETE /requirements/{id}`.

Оценить транскрипт:

```json
POST /evaluate
{
  "client_id": "client_abc",
  "transcript": "00:00 Менеджер: Здравствуйте, меня зовут ...",
  "score_scale": null
}
```

`score_scale` можно не передавать. Если шкала задана, она включается в промпт и модель должна выставить числовую оценку строго по ней. Статусы критериев: `fulfilled`, `partially_fulfilled`, `not_fulfilled`, `insufficient_information`, `not_applicable`, `conflict`.

`POST /search` оставлен для семантического поиска и проверки релевантности; `POST /evaluate` использует полный активный чек-лист, чтобы не пропускать критерии из-за ограничения top-k.

## Замена модели

LLM задаётся через `LLM_BASE_URL`, `LLM_API_KEY` и `LLM_MODEL`; требуется OpenAI-совместимый API. Модель эмбеддингов задаётся через `EMBEDDING_MODEL`, устройство — `EMBEDDING_DEVICE`. При замене embedding-модели нужно одновременно пересоздать/мигрировать коллекцию и выставить правильный размер вектора в `config.py`.

## Важные ограничения перед эксплуатацией

- Таблица `rag_requirements` создаётся автоматически. Существующие записи из прежней версии, которые были загружены только в vector store, нужно повторно загрузить через `/requirements`; иначе они не попадут в полный чек-лист оценки.
- При обновлении правила с `id` хранится только актуальная запись и её номер версии; история текста для аудита пока не ведётся.
- API предназначен для внутреннего вызова доверенным backend. Перед публикацией наружу нужно добавить аутентификацию, tenant authorization, лимиты запросов и ограничение размера транскрипта.
- Полный транскрипт и все активные правила отправляются одним запросом к LLM. Это следует проверить на реальных длинных звонках и лимитах контекста выбранной модели.
- Точные цитаты проверяются на наличие в исходном транскрипте; speaker и timestamp сохраняются, если модель их вернула.
- Качество ещё требует калибровки на обезличенном массиве звонков вместе с заказчиком.
