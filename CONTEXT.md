# Project Context: SaaS-платформа для контроля качества звонков
> **Инструкция для AI-агента:** Используй этот файл как основной источник правды о проекте. При генерации кода, проектировании архитектуры и ответах на вопросы строго придерживайся указанного стека, архитектурных принципов (особенно модульности и заменяемости) и актуального скоупа задач.

## 1. Общее описание и бизнес-цель
**Название:** SaaS-платформа для контроля качества звонков (`SaaS-voice-analysis`)
**Заказчик:** СБЕР + «Плинар»
**Кураторы / Менторы:** Ларин Евгений (техноментор, `@Volkoshkursk`), И.С. Блеканов, Севрюков С.Ю.

**Проблема:** Руководитель отдела продаж (РОП) физически может прослушать лишь 2–5% звонков из CRM Битрикс24, из-за чего теряются лиды и нарушаются скрипты продаж.
**Цель проекта:** Разработать систему автоматического контроля 100% звонков в записи (не real-time). Система должна забирать аудиозаписи из CRM, транскрибировать их, оценивать диалог с помощью LLM по динамическому чек-листу с подробной аргументацией и выводить результаты в «Кабинет РОПа».
**Целевые KPI бизнеса:** 100% охват звонков, экономия до 80% времени РОПа на аудит.

## 2. Актуальный скоуп (Приоритеты после созвона с заказчиком)
*Внимание: В первоначальном описании проекта были модули, которые заказчик решил отложить. Ориентироваться нужно на список ниже.*

### Входит в текущий этап разработки (In Scope):
1. **Интеграция с CRM (Битрикс24):** Получение записей звонков (только аудиодорожки, без видео) по REST API после завершения звонка.
2. **Предобработка и Транскрибация (STT):** Обработка аудио (включая VAD — детекцию голосовой активности) и перевод в текст с помощью модели **Whisper**.
3. **Оценка диалогов (LLM):** Проверка звонка с помощью модели **Qwen** на соответствие базовым правилам и динамическому чек-листу (скрипту), который вносится до звонка. Выдача детальной текстовой аргументации оценки и рекомендаций менеджеру.
4. **Web-интерфейс (Кабинет РОПа + Админка):**
   - Просмотр списка сотрудников и их звонков.
   - Аудиоплеер для прослушивания звонка + визуальная разметка дорожки по этапам диалога (приветствие, скрипт, ответ клиента и т.д.).
   - Отображение детальной оценки от LLM.
   - UI-конструктор чек-листов (скриптов) и промптов.
   - Кабинет администратора: управление пользователями, ролями (СОП / РОП / Админ) и лимитами (токены, архив звонков).

### Отложено на будущие этапы (Out of Scope сейчас, но заложить в архитектуру):
- **Модуль «Патруль» (анализ просроченных задач из CRM, штрафы/поощрения):** Сейчас НЕ реализуем. Архитектура должна позволять легко подключить его позже как отдельный плагин/сервис.
- **HR-сигналы и «Тревожные ситуации»:** Пока не рассматриваем (фокус только на базовых требованиях и чек-листе).

## 3. Архитектурные принципы и Нефункциональные требования (КРИТИЧНО)
1. **ЭКСТРЕМАЛЬНАЯ МАСШТАБИРУЕМОСТЬ И МОДУЛЬНОСТЬ:**
   - Главный запрос заказчика — легкая взаимозаменяемость любого компонента без переписывания архитектуры (Слабая связанность / Loose Coupling, Clean/Hexagonal Architecture, паттерны Strategy/Adapter).
   - **Модели (STT/LLM):** Должна быть возможность в любой момент заменить Whisper/Qwen на GigaChat или другое API/локальную модель простым переключением конфига или написанием тонкого адаптера.
   - **CRM:** Источник данных должен быть абстрагирован (сейчас пишем Mock API -> затем Битрикс24 -> потенциально другая CRM).
2. **Асинхронность и Очереди:**
   - Обязательное использование брокера сообщений / очередей задач для пайплайна обработки звонков.
   - SLA на обработку: не более **30–40 минут** на пакет данных клиента. Избыточная низкоуровневая оптимизация под хайлоад сейчас не нужна, достаточно правильной архитектуры с очередями.
3. **Безопасность:** Учет политик работы с персональными данными (ПДн), тестирование проводится на обезличенных массивах звонков.

## 4. Технический стек и Инфраструктура
- **Frontend:** React, TypeScript.
- **Backend (Core / API / Бизнес-логика):** Node.js, TypeScript (обязательное требование заказчика).
- **ML-сервис и Оркестрация моделей (Audio preprocessing, STT, LLM):** Python.
- **База данных:** PostgreSQL (допустим SQLite для локальных тестов/моков).
- **Очереди:** (например, RabbitMQ / Redis + BullMQ / Celery — для связи Node.js и Python воркеров).
- **ML Модели:** 
  - STT: **Whisper**
  - LLM: **Qwen**
  - *Где крутятся:* Модели развертываются локально (не облачное API). На текущем этапе используются мощности сервера СПбГУ (или локально через Ollama для разработки), позже заказчик предоставит свои доступы. Взаимодействие между бэкендом и моделями — по сети (HTTP/gRPC/Очереди).
- **Инфраструктура и Деплой:** Docker, Docker Compose, Ubuntu, GitHub Actions (CI).

## 5. Пайплайн работы системы (Data Flow)
1. **Pre-call:** СОП (сотрудник отдела продаж) или РОП через UI вносит/настраивает чек-лист (скрипт) и требования к звонку.
2. **Ingest:** После звонка в Битрикс24 воркер загрузки (по REST API) забирает аудиофайл звонка и метаданные.
3. **Queue:** Задача на обработку ставится в очередь.
4. **Audio Prep & STT (Python):** Аудио проходит предобработку и VAD (детекцию голоса), затем транскрибируется через Whisper.
5. **LLM Evaluation (Python):** Транскрипт + динамический чек-лист отправляются в Qwen. Модель возвращает структурированный ответ (оценка, аргументация, таймкоды/классификация реплик, рекомендации).
6. **Storage & UI (Node.js + React):** Результаты сохраняются в PostgreSQL и отображаются в Dashboard РОПа.

## 7. Организационные правила разработки
1. **Прозрачность кода:** Заказчик имеет прямой доступ к GitHub-репозиторию и регулярно просматривает коммиты/PR. Код должен быть чистым, читаемым, с понятной историей коммитов и документацией.
2. **Итеративность и Демо:** Разработка ведется модулями (например: модуль загрузки -> модуль транскрибации -> модуль оценки). По завершении каждого логического этапа проводится созвон с заказчиком и демонстрация работающего функционала (Demo).
